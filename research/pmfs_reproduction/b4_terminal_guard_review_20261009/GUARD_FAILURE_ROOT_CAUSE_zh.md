# 运行保护误判根因：观察者时钟陈旧

判决：`CONFIGURATION_OR_RUNTIME_FAULT / EXECUTED_GUARD_INTEGRATION_FAIL`。

执行版本的保护器把`node.get_clock().now()`的单次读数增量除以保护器自身的轮询墙钟间隔，假设两次客户端读数都新鲜。该假设不成立。

`runtime_driver.py`在预检中同步执行四次`ros2 param dump`；等待这些子进程时没有继续`rclpy.spin_once`。仿真与播放器继续运行，采集节点缓存的ROS时间和传感器消息滞后。恢复spin后，节点补收/追赶，保护器把观察者追赶当作真实发布者时钟跳变。

| 证据 | 保存数值 |
|---|---:|
| goal记录的客户端ROS秒 | 55.801567090 |
| 第一次保护检查客户端ROS秒 | 96.301331410 |
| 两次客户端读数差 | 40.499764320秒 |
| 保护器墙钟间隔 | 0.194343643秒 |
| 独立播放器时间记录数 | 604 |
| 播放器记录最大间隔 | 0.505457410秒 |
| 播放器逆向步 | 0 |

`CLOCK_BACKLOG_REGRESSION.json`用实际第一行事件重新调用**真正执行的政策**，精确复现DRAIN/ROS_CLOCK_FORWARD_JUMP。`verify_b4_terminal.py`又从原始记录重算上述数值及物理气体帧配对。原CDR的时钟订阅也有消息缺口，不能将采集缺口当作发布者跳变；独立播放器记录是必要的交叉证据。

本轮记录支持客户端积压解释，不支持真实40.5秒全局跳变。四次CLI转储没有逐条记录起止单调墙钟，因此不伪造每次CLI耗时。没有把此新证据倒推成第一次B4的精确官方startTime。

为什么12项测试没有挡住：合成事件只覆盖“两个时钟采样都新鲜”的情形，未包含ROS执行器堵塞和缓存追赶。原PASS是真实测试结果，但不足以放行实际集成；追加实际记录的回归后该执行版本FAIL。

最小修正提案，均未启动GSL：

1. CLI参数转储改成Popen，等待时继续spin，并检查退出状态；补丁为`offline_proposal/PREGOAL_PARAMETER_DUMP_FIX.patch`。
2. 客户端单次时钟大步只记录为未资格化异常，不能自动认定发布者发生跳变。只有独立、可信的发布者证据才允许时钟跳变取消；仍保留345墙钟秒、15墙钟秒无推进、进程退出与结果优先处理。详见`CLOCK_OBSERVER_FIX.patch`和提案政策。
3. 实际发布者跳变会使运行物理时间资格HOLD，不能因为Action返回就恢复物理PASS。当前没有部署提供`confirmed_clock_discontinuity`的发布者证据适配器，提案不冒充端到端验收。

提案的14项测试包含实际40.5秒追赶、初始化延迟、官方成功/失败、结果/取消邻近、硬墙钟门、停滞/恢复、未资格化逆向采样、经证据确认的前后跳变以及进程异常。它们证明离线决策规则，不能代替新运行；第三次goal没有授权，未执行。

取消后GSL进入非法goal结果发布路径并退出-6，属于单独的取消/关闭异常。完整源码和日志保留，未修PMFS二进制，未仅凭本次取消宣称上游科学缺陷。
