GeoPT's released representation is substantially more compatible with indoor gas transport than a surface-only reading of the paper suggested.

## 1. GeoPT volume representation

The official `DrivAerML_process.py` explicitly processes both surface and volume CFD data.

For volume cells it constructs:

[
x_{m vol}
=
[x,y,z,mathrm{SDF},d_x,d_y,d_z].
]

Where:
- ((x,y,z)): volume cell center;
- SDF: unsigned distance to nearest boundary;
- ((d_x,d_y,d_z)): direction from nearest boundary to the volume point.

For boundary points it uses:

[
x_{m surf}
=
[x,y,z,0,n_x,n_y,n_z].
]

Thus GeoPT already learns a common representation for:
- interior volume points;
- boundary surface points.

This is directly relevant to obstacle-rich indoor transport.

## 2. Dynamics prompt structure

Official GeoPT fine-tuning scripts use:

- `space_dim = 3`;
- `fun_dim = 11`.

The data loader supplies the 7-D geometry/volume feature above.

`GeoPT_finetune.py` then appends a 4-D dynamics field generated by `dynamics_config.py`.

Typical dynamics representation is:

[
[v_x,v_y,v_z,mathrm{magnitude/extra}].
]

The resulting 11-D feature enters the same pre-trained input embedding.

## 3. Near-direct gas mapping

For an indoor gas free-space point (x), construct:

[
g(x)
=
[x,y,z,d_{m wall}(x),n_x^{wall},n_y^{wall},n_z^{wall}].
]

Where:
- (d_{m wall}): distance to nearest occupied/boundary cell;
- (n^{wall}): normalized direction relative to nearest wall/boundary.

Construct the 4-D gas dynamics prompt:

[
v_{m gas}(x)
=
[
hat w_x(x),
hat w_y(x),
hat w_z(x),
|w(x)|
].
]

Then

[
f_{m input}(x)
=
[g(x),v_{m gas}(x)]
inmathbb R^{11}.
]

This preserves:
- GeoPT input dimensionality;
- geometry semantics;
- dynamics-vector semantics;
- the pre-trained first-layer shape.

This is a strong interface match.

## 4. Source conditioning problem

The remaining PMFS-specific variable is candidate source location (s).

Adding source channels directly to the 11-D input would change `preprocess.linear_pre` shape and prevent full loading of the input embedding weights.

Therefore **do not concatenate source coordinates to the raw input** in the first probe.

## 5. Proposed gas-specific second innovation — Source Injection Adapter

Preserve the full pretrained geometry+wind backbone.

Encode candidate source relative to each query point:

[
r_s(x)
=
[
x-s,;
|x-s|,;
Q_s(x)
].
]

Use a small source encoder:

[
z_s(x)
=
E_s(r_s(x)).
]

Inject it *after* GeoPT's pretrained input projection:

[
h_0(x)
=
E_{m GeoPT}(g(x),v_{m gas}(x))
+
A_s(z_s(x)).
]

Alternative:
- FiLM modulation of selected GeoPT blocks using candidate-source embedding.

Requirements:
- GeoPT pretrained input embedding remains unchanged;
- the source adapter is small relative to the backbone;
- source-only adapter is trained from plume data;
- random-backbone / no-pretrain control is mandatory.

Interpretation:

> GeoPT supplies a pretrained **environment transport representation**; the source adapter injects the counterfactual PMFS source hypothesis into that physical environment.

## 6. PMFS integration

For each PMFS source candidate (s):

1. keep environment tokens ((geometry,wind)) fixed;
2. change only the source adapter input;
3. predict candidate plume/hit field;
4. update PMFS source probability.

This is computationally attractive because environment embeddings can potentially be cached across all source candidates.

A future optimization should test:

[
H_{m env}
=
{m GeoPT}(geometry,wind)
]

once per source update, followed by cheap candidate-specific source adapters.

## 7. Why this is stronger than generic PINO

Generic PINO:
- trains geometry/wind/source representation from plume data.

Proposed M6:
- imports a pretrained geometry–dynamics representation;
- preserves its volume/boundary semantics;
- learns only gas-specific source injection and downstream plume mapping.

This is the exact foundation-model transfer hypothesis.

| tokens | median CPU forward |
|---:|---:|

These are **not official GeoPT benchmark numbers** and do not include checkpoint loading or source adapter. They show only that PMFS-scale 2-D free-space token counts are far below the mesh sizes GeoPT is designed for.

Inference/token count is therefore not currently a primary M6 risk.
